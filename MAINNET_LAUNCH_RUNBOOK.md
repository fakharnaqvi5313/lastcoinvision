# Mainnet Launch Runbook — DRAFT, NOT EXECUTABLE YET

This is a planning document, not instructions to run today. It exists so the actual sequence
of steps is ready and reviewed before it's needed, not improvised under launch-day pressure.
**Do not begin step 1 of §2 until every gate in §1 is checked.** Unlike `lcv-testnet-1`, a
mainnet genesis is not something to wipe and restart if something's wrong — treat every gate
below as a hard blocker, not a formality.

## 1. Hard gates (must all be true before this runbook can be executed)

As of 2026-08-05, **none of these are closed**. This section should be re-read and honestly
re-checked immediately before anyone treats §2 as actionable — don't let it go stale.

- [ ] **Professional security audit complete, and every finding either fixed or explicitly
      accepted in writing.** `AUDIT_SCOPE.md` exists to brief an auditor; no audit has started.
      Automated scanning (gosec/staticcheck/fuzzing/Slither/cargo audit/npm audit) is not a
      substitute — see `AUDIT_SCOPE.md`'s own framing of what it does and doesn't cover.
- [ ] **Treasury and ecosystem multisigs are real** — signer keys generated by genuinely
      separate people on genuinely separate machines, not the current one-machine ceremony
      (see DECISIONS.md, 2026-08-05). A single-machine "multisig" is not a multisig for
      security purposes; it's a same-day placeholder that happens to look like one on-chain.
- [ ] **Team, investors, public, and community addresses are real custody**, not the current
      single-key, one-machine placeholders (see DECISIONS.md, 2026-08-05). `public`'s address
      is also blocked on deciding an actual distribution mechanism — the address is secondary
      to that decision, not the other way around.
- [ ] **A real, independent, economically diverse validator set is recruited and onboarded**,
      each meeting §2 of `RELEASE_CHECKLIST.md` (dedicated hardware, HSM/remote-signer-backed
      consensus keys, sentry-node topology — now verified working end-to-end via `deploy/k8s/`,
      2026-08-05 — or an equivalent non-k8s setup). `lcv-testnet-1` today is one team-hosted
      bootstrap node; that satisfies "dry run privately," nothing more. A mainnet with one
      validator, or a handful all controlled by the same people, isn't decentralized — it's a
      single point of failure with extra steps.
- [ ] **Legal and regulatory review of the tokenomics is complete**, with real counsel, before
      any real value is at stake. Nothing in this repo constitutes that review.
- [ ] **A real bug bounty program is live**, or a documented decision that mainnet launches
      without one and why — `SECURITY.md`'s current "no bug bounty, devnet/testnet-stage,
      no real value at stake" framing stops being accurate the moment mainnet has real value.
- [ ] **`lcv-testnet-1` (or a successor testnet) has run under real conditions for a
      meaningful stretch of time** — uptime, real transaction volume, at least one real
      governance-triggered upgrade rehearsed on a persistent (not disposable-devnet) network.
      Not "it started and produced blocks for a few days."

## 2. Mainnet genesis construction

Adapted from `scripts/genesis/init-testnet-genesis.sh`, which remains the reference for the
actual mechanics (real vesting math, validator self-bond carved from the `public` allocation
rather than minted, real governance timing, `gengenesis`'s built-in refusal to proceed if
percentages don't sum to 100). What's different for mainnet:

1. **Confirm every §1 gate is closed**, in writing, with whoever has authority to make that
   call — not assumed from this document's own checklist state.
2. **Final allocation address review.** Every one of the six bucket addresses
   (`scripts/genesis/allocation-addresses.local.sh` or wherever real values end up living)
   must be independently re-verified by at least two people against the real custody
   arrangements — not just "it's the address we generated," but confirmed against whatever
   record (multisig ceremony minutes, custody provider statement, etc.) proves who actually
   controls it. A wrong address here is permanent and unrecoverable.
3. **Decide the real validator set and each one's self-bond** before genesis, not after —
   unlike `lcv-testnet-1`'s single bootstrap validator, a real launch needs every validator's
   gentx collected and verified (`RELEASE_CHECKLIST.md` §2's "Gentx submitted and verified"
   item, done here for real, not trivially with one validator).
4. **Run `gengenesis` with the real addresses, real validator self-bond carve-outs, and real
   ITN reward file if applicable** (`-itn-rewards-file`, see DECISIONS.md 2026-08-05 for what
   this does) — dry-run the exact command that will produce the real genesis at least once
   against a disposable copy first, and diff the two runs' output to confirm determinism.
5. **`lcvd genesis validate-genesis`**, then **independently re-verify the total supply and
   every bucket's amount by summing genesis balances directly** (not trusting `gengenesis`'s
   own summary output) — the same rigor used to verify `lcv-testnet-1`'s genesis
   (`RELEASE_CHECKLIST.md` §1), but done by someone other than whoever ran `gengenesis`.
6. **Freeze genesis.** From this point, `genesis.json` is immutable. Compute and publish its
   hash.

## 3. Validator coordination

1. **Distribute the frozen genesis + persistent_peers/seeds list** to every validator.
   Every validator independently confirms their local genesis.json hash matches the published
   one before proceeding — mismatches here mean someone doesn't launch, not that the network
   proceeds with a silent fork risk.
2. **Dry-run among a broader set than just the launch coordinator** — every validator, or a
   representative subset, rehearses against the real genesis on a private network first.
   `lcv-testnet-1`'s existing "dry run" only ever covered one validator; mainnet needs this
   done with real external validators before the real launch, not assumed to generalize.
3. **Publish the launch time**, far enough out that every validator can be started and waiting
   before it. Confirm each has started and is waiting at that height.

## 4. Launch

1. **At genesis time**, confirm the chain produces its first block and that 2/3+ voting power
   is online (`lcvd query staking validators`, cross-checked against `lcvd status` on multiple
   independent validators, not just the launch coordinator's own).
2. **Re-verify every module's acceptance criteria on the real network** — the same flows
   already proven on `lcv-testnet-1` (identity's create-did/query round-trip; registry,
   taxrail, and voting's gov-gated bootstrap; a real governance-driven param change) — proven
   again here, not assumed to carry over from the testnet run.
3. **Stand up faucet/explorer/RPC/API** pointed at the real network — `deploy/docker-compose/`
   or `deploy/k8s/` (now verified end-to-end, 2026-08-05), whichever was chosen for real
   validator infrastructure.
4. **Confirm the security posture is live**: `SECURITY.md`'s reporting channel monitored, the
   bug bounty program (§1) actually running, `AUDIT_SCOPE.md`'s findings re-confirmed against
   this network's real genesis parameters, not just the testnet's.

## 5. Post-launch

1. **Announce.** Only now — remove every "testnet/devnet" disclaimer from public-facing
   surfaces (`web/`, `docs/`) that this runbook's §1 gates have made obsolete, and only those.
   No legal, investment, or regulatory-approval language, matching the constraint that already
   applies to every other public surface in this repo.
2. **Monitor real-condition operation** — missed blocks, validator distribution of stake
   (is any single entity approaching a concerning share of voting power?), real transaction
   patterns, anything the testnet run didn't surface because it never had real economic
   activity.
3. **Keep the cosmovisor upgrade path rehearsed and ready** — `lcv-testnet-1`'s rehearsal was
   deliberately deferred (DECISIONS.md, 2026-08-04); mainnet should not defer this
   indefinitely once real governance-triggered upgrades become likely.

## Explicit non-goals

- **No "soft launch."** Either every §1 gate is closed and this is a real, announced mainnet,
  or it isn't launched. A quiet launch with unresolved custody/audit/legal gates is not lower
  risk than a loud one — it's the same risk with worse incident response, since no one's
  watching for problems.
- **No partial announcement** ahead of legal/regulatory sign-off, regardless of technical
  readiness. Technical readiness and launch readiness are different gates; closing the first
  doesn't close the second.
