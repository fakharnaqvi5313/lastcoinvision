# Multisig & Real-Custody Ceremony Runbook — DRAFT, NOT EXECUTED

Planning document for two related `MAINNET_LAUNCH_RUNBOOK.md` §1 gates: *"treasury and
ecosystem multisigs are real"* and *"team, investors, public, and community addresses are real
custody."* Both currently point at single-key, one-machine placeholders generated in one sitting
(see `DECISIONS.md`, 2026-08-05) — deliberate, documented placeholders for testnet, not something
to carry into a mainnet genesis.

**This document does not generate any real keys.** A genuine multisig/custody ceremony is a
coordination exercise between real, separate people — its entire value comes from nobody
(including this agent, including a single operator working alone) being able to unilaterally
reconstruct the full key set. Running it here would defeat the point as thoroughly as writing
someone else's password down "for convenience" would defeat theirs.

## What makes a multisig actually real

Cosmos SDK multisig accounts (`lcvd keys add --multisig`) are threshold-signature accounts:
`k`-of-`n` named signer keys, where `k` signatures out of the `n` registered public keys are
required to authorize any transaction from that account. The **address** is deterministic from
the set of public keys and the threshold — meaning the account can be created and its address
known before every signer has even generated their key, useful for planning, but the security
property only holds once each signer key genuinely lives with a genuinely separate person:

- **Separate people, not separate hats worn by the same person.** A multisig where all `n` keys
  are generated by the same individual (even on different machines) is not meaningfully
  different from a single key with extra steps — same principle already applied to
  `lcv-testnet-1`'s second validator having to be a real independent operator, not a second copy
  of the first operator (`DECISIONS.md`, 2026-08-05).
- **Separate machines, ideally separate key-management approaches per signer.** If every signer
  uses the same laptop's keyring, a single compromised machine defeats the whole scheme. Mixing
  hardware wallets (Ledger), OS keychains on genuinely different devices, and (for the highest-
  value keys) the same HSM/remote-signer pattern as `VALIDATOR_HSM_RUNBOOK.md` gives real
  defense in depth.
- **A real, deliberate threshold choice.** `2-of-3` tolerates one signer being unavailable or
  compromised; `3-of-5` tolerates two. Higher isn't automatically better — too high a threshold
  risks the account becoming unusable if signers are unreachable (travel, illness, departure).
  This is a judgment call for whoever owns the treasury decision, not something this document
  picks on their behalf.

## Which buckets need what

From the allocation table (`scripts/genesis/init-testnet-genesis.sh`, `DECISIONS.md`):

| Bucket | % | Recommended custody shape | Why |
|---|---|---|---|
| `treasury` (foundation) | 20% | Real multisig, threshold TBD by treasury owner | Largest discretionary-spend bucket — highest value at risk from a single compromised key |
| `ecosystem` (grants) | 25% | Real multisig, threshold TBD | Largest bucket overall; disbursed over time, not a one-time transfer, so ongoing key security matters for years, not one ceremony |
| `team` | 15% | Real custody per-recipient (vesting), not necessarily a multisig | Vesting to individuals is a different shape than a shared discretionary pool — see below |
| `investors` | 15% | Real custody per-recipient (vesting) | Same reasoning as `team` |
| `public` | 8% | Blocked on a distribution-mechanism decision (see `MAINNET_LAUNCH_RUNBOOK.md`) — custody shape depends on what that mechanism turns out to be | Address is secondary to that decision per the existing gate text |
| `community` (airdrop) | 5% | Real multisig for the pre-distribution holding address; individual recipients get their own custody once claimed | Same shape as any airdrop: one held pool, then many individually-owned claims |

`team`/`investors` being "vesting to individuals" rather than "a shared multisig" is worth
being explicit about: `x/auth`'s vesting account types lock a schedule to a *single* address.
Real custody there means each real recipient controls their own vesting address (via whatever
wallet — this project's own `apps/desktop`/`apps/mobile`, a hardware wallet, Keplr, etc.), not
one shared multisig standing in for many people's individual allocations. If `team`/`investors`
are still single pooled addresses at mainnet time, that's a distinct problem from "not a real
multisig" — it's "not actually allocated to individuals yet," worth flagging to whoever owns
that decision rather than assumed away.

## Ceremony procedure (for the two real multisig buckets: `treasury`, `ecosystem`)

1. **Identify real, separate signers** — named people, not placeholder roles, each with their
   own key-management setup. Document who they are and why they were chosen (this becomes part
   of the record `MAINNET_LAUNCH_RUNBOOK.md` §1 needs to actually check this gate closed).
2. **Each signer generates their own key independently**, on their own device, using whatever
   method suits their own security posture (hardware wallet, this project's own wallet apps, a
   dedicated air-gapped machine for the highest-value bucket) — never generated by one person or
   one script on behalf of everyone. See [`SIGNER_SETUP.md`](SIGNER_SETUP.md) for a ready-to-send
   guide covering this exact step (both the desktop wallet app and the CLI).
3. **Collect public keys only** (never private keys) from each signer through a channel that
   lets each signer verify what they sent — a signed message, an in-person/video confirmation,
   or at minimum a second channel to cross-check the pubkey wasn't altered in transit.
4. **Construct the multisig account** from those public keys and the chosen threshold. This is
   two steps with the actual `lcvd keys` CLI, not one: first import each signer's public key
   into the constructing machine's local keyring as a named entry
   (`lcvd keys add <signer-name> --pubkey-base64 <their-pubkey>` — this step handles only a
   public key, never anything secret), then build the multisig from those names
   (`lcvd keys add <multisig-name> --multisig "<signer1-name>,<signer2-name>,..."
   --multisig-threshold <k>`). Either step can be run by anyone holding the collected pubkeys —
   no private key material is ever needed to derive the deterministic multisig address.
5. **Test the threshold on a real signed transaction against `lcv-testnet-1` first** (a small,
   inconsequential transfer) — confirming the actual signers can actually produce a valid
   `k`-of-`n` signature together before this address is ever used for a real mainnet allocation.
6. **Record the ceremony**: who the signers are, how each key was generated, the threshold, and
   the test-transaction evidence — this is what lets `MAINNET_LAUNCH_RUNBOOK.md`'s gate be
   checked against real evidence instead of a claim, matching the pattern already established
   for the audit and HSM gates.

## What this document does not decide

The actual threshold values, who the real signers are, and the `public` bucket's distribution
mechanism are all decisions for whoever has the authority to make them — not something to
default or infer here. This runbook is ready to execute the moment those decisions are made;
it doesn't make them.
